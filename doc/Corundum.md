# Corundum架构
Corundum 具有几个独特的架构特性。首先，硬件队列状态被高效地存储在 FPGA 块 RAM 中，从而能够支持数千个可独立控制的队列。这些队列与接口相关联，每个接口可以有多个端口，每个端口都有自己独立的传输调度器。这使得对数据包传输的控制能够达到极高的细粒度。调度器模块的设计允许进行修改或完全替换，以实现不同的传输调度方案，包括实验性的调度器。结合 PTP 时间同步，这支持基于时间的调度，包括高精度的时分多址（TDMA）。

Corundum 的设计具有模块化和高度参数化的特点。许多配置和结构选项可以在综合时通过 Verilog 参数进行设置，包括接口和端口数量、队列数量、内存大小、调度器类型等。这些设计参数在配置寄存器中暴露，驱动程序通过读取这些寄存器来确定 NIC 的配置，使得同一个驱动程序无需修改就能支持许多不同的板卡和配置。

当前设计支持用于 Xilinx Ultrascale PCIe 硬核 IP 核接口的 PCIe DMA 组件。对于其他 FPGA 中常用的 PCIe TLP 接口的支持尚未实现，这是未来的工作方向。这种支持将使 Corundum 能够在更多种类的 FPGA 上运行。

Corundum 的占用空间相当小，即使在相对较小的 FPGA 上也能留下充足的空间用于添加额外的逻辑。例如，针对 ExaNIC X10 的 Corundum 设计是一个双端口 10G 设计，具有 PCIe gen 3 x8 接口和 512 位内部数据路径，其消耗的逻辑资源不到第二小的 Kintex Ultrascale FPGA（KU035）可用资源的四分之一。

#### 1. 高层概述
Corundum NIC 的框图如图 1 所示。从高层来看，NIC 由 3 个主要的嵌套模块组成。顶层模块主要包含支持和接口组件。这些组件包括 PCIe 硬核 IP 核和 DMA 接口、PTP 硬件时钟，以及以太网接口组件（包括 MAC、PHY 和相关的串行器）。顶层模块还包含一个或多个接口模块实例。每个接口模块对应一个操作系统级别的网络接口（例如 eth0）。每个接口模块包含队列管理逻辑以及描述符和完成处理逻辑。队列管理逻辑维护所有 NIC 队列的状态——传输队列、传输完成队列、接收队列、接收完成队列和事件队列。每个接口模块还包含一个或多个端口模块实例。每个端口模块提供一个 AXI 流接口到 MAC，并包含一个传输调度器、传输和接收引擎、传输和接收数据路径，以及一个暂存 RAM（用于在 DMA 操作期间临时存储传入和传出的数据包）。

![图1 Corundum NIC 框图](/images/Corundum_architecture.jpg "Corundum architecture")

对于每个端口，端口模块中的传输调度器决定哪些队列被指定用于传输。传输调度器生成命令给传输引擎，以启动从 NIC 传输队列的传输操作。调度器模块设计为可以修改或完全替换，以实现不同的传输调度方案，包括实验性的调度器。与 PTP 时间同步相结合，这支持基于时间的调度，包括高精度的 TDMA。

在接收方向，传入的数据包通过流哈希模块，以确定目标接收队列，并生成命令给接收引擎，以协调接收数据路径上的操作。由于同一接口模块中的所有端口共享同一组接收队列，不同端口上的传入流会合并到同一组队列中。也可以在 NIC 中添加定制模块，在数据包通过 PCIe 总线之前对其进行预处理和过滤。

NIC 上的组件通过几种不同的接口互连，包括 AXI lite、AXI 流，以及用于 DMA 操作的定制分段内存接口。AXI lite 用于从驱动程序到 NIC 的控制路径。它用于初始化和配置 NIC 组件，以及在传输和接收操作期间控制队列指针。AXI 流接口用于在 NIC 内部传输打包数据，包括 PCIe 传输层数据包（TLP）和以太网帧。分段内存接口用于将 PCIe DMA 接口连接到 NIC 数据路径以及描述符和完成处理逻辑。

NIC 的大部分逻辑在 PCIe 用户时钟域中运行，当前所有设计变体的标称频率为 250 MHz。异步 FIFO 用于与 MAC 接口，MAC 在适当的串行器传输和接收时钟域中运行——10G 为 156.25 MHz，25G 为 390.625 MHz，100G 为 322.266 MHz。

以下各节描述 NIC 内的几个关键功能块。

#### B. 流水线队列管理
Corundum NIC 和驱动程序之间的数据包通信通过描述符和完成队列进行调解。描述符队列形成主机到 NIC 的通信通道，携带有关单个数据包在系统内存中的存储位置的信息。完成队列形成 NIC 到主机的通信通道，携带有关已完成操作和相关元数据的信息。描述符和完成队列实现为驻留在 DMA 可访问系统内存中的环形缓冲区，而 NIC 硬件维护必要的队列状态信息。这种状态信息包括指向环形缓冲区的 DMA 地址的指针、环形缓冲区的大小、生产者和消费者指针，以及对相关完成队列的引用。每个队列所需的描述符状态为 128 位。

Corundum NIC 的队列管理逻辑必须能够高效地存储和管理数千个队列的状态。这意味着队列状态必须完全存储在 FPGA 上的块 RAM（BRAM）或超 RAM（URAM）中。由于需要 128 位 RAM，而 URAM 块为 72x4096，存储 4096 个队列的状态只需 2 个 URAM 实例。利用 URAM 实例使队列管理逻辑能够扩展到每个接口至少处理 32,768 个队列。

为了支持高吞吐量，NIC 必须能够并行处理多个描述符。因此，队列管理逻辑必须跟踪多个正在进行的操作，随着操作的完成向驱动程序报告更新的队列指针。跟踪正在进行的操作所需的状态比描述符状态小得多，因此可以存储在触发器和分布式 RAM 中。

NIC 设计使用两个队列管理器模块：queue_manager 用于管理主机到 NIC 的描述符队列，而 cpl_queue_manager 用于管理 NIC 到主机的完成队列。这两个模块相似，只是在指针处理、填充处理以及门铃/事件生成方面存在一些细微差别。由于相似性，本节仅讨论 queue_manager 模块的操作。

用于存储队列状态信息的 BRAM 或 URAM 阵列每次读取操作需要几个周期的延迟，因此 queue_manager 采用流水线架构，以促进多个并发操作。该流水线支持四种不同的操作：寄存器读取、寄存器写入、出队/入队请求以及出队/入队提交。通过 AXI lite 接口的寄存器访问操作使驱动程序能够初始化队列状态，提供指向已分配主机内存的指针，以及在正常操作期间访问生产者和消费者指针。

#### C. 传输调度器
Corundum NIC 中使用的默认传输调度器是一个简单的轮询调度器，在 tx_scheduler_rr 模块中实现。调度器向传输引擎发送命令，以启动从 NIC 传输队列的传输操作。轮询调度器包含所有队列的基本队列状态、一个用于存储当前活动队列并执行轮询调度的 FIFO，以及一个用于跟踪正在进行的传输操作的操作表。

与队列管理逻辑类似，轮询传输调度器也将队列状态信息存储在 FPGA 上的 BRAM 或 URAM 中，以便能够扩展以支持大量队列。传输调度器还使用处理流水线来隐藏内存访问延迟。

传输调度器模块有四个主要接口：一个 AXI lite 寄存器接口和三个流接口。AXI lite 接口允许驱动程序更改调度器参数并启用/禁用队列。第一个流接口提供来自队列管理逻辑的门铃事件，当驱动程序将数据包入队等待传输时触发。第二个流接口携带调度器生成的传输命令到传输引擎。每个命令包括要传输的队列索引以及用于跟踪正在进行的操作的标签。最后一个流接口将传输操作状态信息返回给调度器。状态信息告知调度器传输的数据包长度，或者如果传输操作由于队列为空或已禁用而失败。

传输调度器模块可以扩展或替换，以实现任意调度算法。这使 Corundum 能够用作评估实验性调度算法的平台，包括 SENIC 、Carousel 、PIEO 和 Loom  中提出的那些算法。也可以为传输调度器模块提供额外的输入，包括来自接收路径的反馈，这可用于实现新的协议和拥塞控制技术，如 NDP 和 HPCC 。将调度器连接到 PTP 硬件时钟可用于支持 TDMA，这可用于实现 RotorNet 、Opera 和其他电路交换架构。

#### D. 端口和接口
Corundum 的一个独特架构特性是端口和网络接口的分离，使得多个端口可以与同一个接口相关联。大多数当前的 NIC 每个接口支持一个端口，如图 2a 所示。当网络栈将数据包入队以在网络接口上传输时，数据包通过与该接口相关联的网络端口注入网络。然而，在 Corundum 中，多个端口可以与每个接口相关联，因此数据包将通过哪个端口注入网络的决定可以由硬件在出队时做出，如图 2b 所示。

![图2 NIC 端口与接口架构对比](/images/NIC_port.jpg "NIC port and interface architecture comparison")

与同一网络接口模块相关联的所有端口共享同一组传输队列，并向操作系统呈现为一个统一的接口。这使得通过仅更改传输调度器设置就可以在端口之间迁移流或在多个端口之间进行负载均衡，而不影响网络栈的其余部分。队列到端口的动态调度器定义映射使 Corundum 能够支持新的协议和网络架构研究，包括并行网络如 P-FatTree [17] 和光交换网络如 RotorNet [18]、Opera [19] 等。

#### E. 数据路径以及传输和接收引擎
Corundum 在数据路径中使用内存映射和流接口。AXI 流用于在端口 DMA 模块、以太网 MAC 以及校验和与哈希计算模块之间传输以太网数据包数据。AXI 流还用于将 PCIe 硬核 IP 核连接到 PCIe AXI lite 主模块和 PCIe DMA 接口模块。定制的分段内存接口用于将 PCIe DMA 接口连接到 NIC 数据路径以及描述符和完成处理逻辑。

AXI 流接口的宽度由所需带宽决定。除以太网 MAC 外，核心数据路径逻辑完全在 250 MHz PCIe 用户时钟域中运行。因此，到 PCIe 硬核 IP 核的 AXI 流接口必须与硬核接口宽度匹配——PCIe gen 3 x8 为 256 位，PCIe gen 3 x16 为 512 位。在以太网侧，接口宽度与 MAC 接口宽度匹配，除非 250 MHz 时钟太慢而无法提供足够的带宽。对于 10G 以太网，MAC 接口为 64 位，156.25 MHz，可以以相同宽度连接到 250 MHz 时钟域。对于 25G 以太网，MAC 接口为 64 位，390.625 MHz，为了在 250 MHz 下提供足够的带宽，需要转换为 128 位。对于 100G 以太网，Corundum 在 Ultrascale Plus FPGA 上使用 Xilinx 100G 硬核 CMAC 核。MAC 接口为 512 位，322.266 MHz，由于需要以约 195 MHz 运行以提供 100 Gbps 带宽，因此以 512 位连接到 250 MHz 时钟域。

NIC 数据路径的框图如图 3 所示，这是图 1 的简化版本。PCIe 硬核 IP 核（PCIe HIP）将 NIC 连接到主机。两个 AXI 流接口将 PCIe DMA 接口模块连接到 PCIe 硬核 IP 核。一个接口用于读写请求，一个接口用于读取数据。然后，PCIe DMA 接口模块通过一组 DMA 接口多路复用器连接到描述符获取模块、完成写入模块、端口暂存 RAM 模块以及 RX 和 TX 引擎。在朝向 DMA 接口的方向上，多路复用器组合来自多个源的 DMA 传输命令。在相反方向上，它们路由传输状态响应。它们还管理用于读写的分段内存接口。顶层多路复用器组合描述符流量和数据包数据流量，给予描述符流量更高的优先级。接下来，一对多路复用器组合来自多个接口模块的流量。最后，每个接口模块内部的一个额外多路复用器组合来自多个端口实例的数据包数据流量。

传输和接收引擎负责协调传输和接收数据包所需的操作。传输和接收引擎可以处理多个正在进行的数据包以实现高吞吐量。如图 1 所示，传输和接收引擎连接到传输和接收数据路径中的多个模块，包括端口 DMA 模块、哈希和校验和卸载模块，以及描述符和完成处理逻辑以及以太网 MAC 的时间戳接口。

传输引擎负责协调数据包传输操作。传输引擎处理来自传输调度器的特定队列的传输请求。经过 PCIe DMA 引擎的低级处理后，数据包将通过传输校验和模块、MAC 和 PHY。一旦数据包发送出去，传输引擎将从 MAC 接收 PTP 时间戳，构建完成记录，并将其传递给完成写入模块。

与传输引擎类似，接收引擎负责协调数据包接收操作。传入的数据包通过 PHY 和 MAC。经过包括哈希和时间戳在内的低级处理后，接收引擎将向 PCIe DMA 引擎发出一个或多个写入请求，以将数据包数据写入主机内存。写入完成后，接收引擎将构建完成记录，并将其传递给完成写入模块。

描述符读取和完成写入模块的操作类似于传输和接收引擎。这些模块处理来自传输和接收引擎的描述符/完成读写请求，向队列管理器发出入队/出队请求以获取主机内存中的队列元素地址，然后向 PCIe DMA 接口发出数据传输请求。完成写入模块还负责处理来自传输和接收完成队列的事件，将它们入队到适当的事件队列中，并写出事件记录。

#### F. 分段内存接口
为了通过 PCIe 实现高性能 DMA，Corundum 使用定制的分段内存接口。该接口分为最大 128 位的段，总宽度是来自 PCIe 硬核 IP 核的 AXI 流接口宽度的两倍。例如，使用 PCIe gen 3 x16 的设计具有来自 PCIe 硬核的 512 位 AXI 流接口，将使用 1024 位的分段接口，分为 8 个 128 位的段。

该接口提供了比使用单个 AXI 接口更好的“阻抗匹配”，通过消除由于 DMA 引擎中的对齐和互连逻辑中的仲裁导致的背压，实现更高的 PCIe 链路利用率。具体而言，该接口保证 DMA 接口可以在每个时钟周期执行全宽度、未对齐的读写操作。此外，使用专用于单方向流量的简单双端口 RAM 消除了读写路径之间的争用。

每个段的操作类似于 AXI lite，但具有三个接口而不是五个。一个通道提供写地址和数据，一个通道提供读地址，一个通道提供读数据。与 AXI 不同，不支持突发和重排序，从而简化了接口逻辑。互连组件（多路复用器）负责保持操作的顺序，即使在访问多个 RAM 时也是如此。段完全独立运行，具有单独的流控制连接和单独的互连排序逻辑实例。此外，操作基于单独的选择信号而不是地址解码进行路由。此功能消除了分配地址的需要，并使使用可参数化的互连组件成为可能，这些组件以最小的配置适当地路由操作。

字节地址映射到分段接口地址，其中最低位地址位确定段中的字节通道，接下来的位选择段，最高位确定该段的字地址。例如，在 1024 位分段接口中，分为 8 个 128 位的段，最低 4 位地址位将确定段中的字节通道，接下来的 3 位将确定段。其余位确定该段的地址总线。

#### G. 设备驱动程序
Corundum NIC 通过内核模块连接到 Linux 内核网络栈。该模块负责初始化 NIC、注册内核接口、为描述符和完成队列分配 DMA 可访问缓冲区、处理设备中断，以及在 kernel 和 NIC 之间传递网络流量。

NIC 使用寄存器空间来暴露参数，包括接口数量、端口数量、队列数量、调度器数量、最大传输单元（MTU）大小，以及 PTP 时间戳和卸载支持的存在。驱动程序在初始化期间读取这些寄存器，以便配置自身并注册与 NIC 设计配置匹配的内核接口。这种自动检测功能意味着驱动程序和 NIC 是松散耦合的；在不同的 FPGA 板卡、不同的 Corundum 设计变体和不同的参数设置上使用时，驱动程序通常不需要针对核心数据路径进行修改。

#### H. 仿真框架
Corundum 包含一个广泛的开源、基于 Python 的仿真框架来评估完整设计。该框架使用 Python 库 MyHDL 构建，包括 PCI express 系统基础设施、PCI express 硬核 IP 核、NIC 驱动程序和以太网接口的仿真模型。该仿真框架通过提供整个系统状态的可见性，便于调试完整的 NIC 设计。

PCIe 仿真框架的核心由大约 4,500 行 Python 代码组成，包括 PCIe 基础设施组件的事务层模型，包括根复合体、功能、端点和交换机，以及高级功能，包括配置空间、功能、总线枚举、根复合体内存分配、中断等。另外的模块（由另外 4,000 行 Python 代码组成）提供 FPGA PCIe 硬核 IP 核的模型，与仿真的 PCIe 基础设施交换事务层流量，并驱动可连接到协同仿真的 Verilog 设计的信号。
